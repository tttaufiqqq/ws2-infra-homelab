# CI

This article explains how the test workflow ran on a self-hosted GitHub Actions runner, and the four incidents found when it first ran on real hardware. Deploy on green is covered in [CD](12-cd.md). The workflow itself is kept at [`examples/tests.yml`](examples/tests.yml), and it no longer runs because the homelab is gone.

## 1. Overview

`tests.yml` runs the backend suite (`Unit`, `Feature`, `Procedures`) on every push and pull request to `main`. A separate `browser` job (Pest 4 and Playwright) runs after it. Both jobs use the runner labels `[self-hosted, linux, homelab, tailnet]`.

The runner is self-hosted because the tests need to reach the Tailscale-only database servers. A GitHub-hosted runner has no path to them without exposing the databases publicly or giving Tailscale credentials to GitHub Secrets. Both are worse than running inside the tailnet.

The runner's container, threat model and scoped Vault token are documented in the [homelab repository](https://github.com/tttaufiqqq/oracle-db-linux-proxmox) (`docs/09-github-actions-runner/actions-runner-setup.md`).

### 1.1 Why two jobs

| Setting | Reason |
|---|---|
| `browser` has `needs: backend` | The runner has one CPU core, so two `artisan` and `npm` processes would contend, not run faster |
| `concurrency: group: tests-shared-db` | The five databases are real shared servers reset by `db:fresh-all`, so two runs at once would stomp on each other |
| `cancel-in-progress: false` | Cancelling a run mid-reset would leave tables half dropped |

## 2. Incident 1: `setup-php` fails on every run

**Symptom:** the first run on real hardware (the file existed earlier but was first pushed on 2026-07-19) failed every job at `shivammathur/setup-php@v2`.

```
ENOENT: no such file or directory, open '/home/run-gh-runner/actions-runner/_work/_actions/shivammathur/setup-php/v2/src/scripts/linux.sh'
```

The path `/home/run-gh-runner/...` does not exist. The real one is `/home/linux-gh-runner/...`. The child Node process exited in 60 ms, far too fast for any install logic, so the failure was in path resolution.

**Cause:** a bug in the action's compiled code (version 2.37.2, `dist/index.js`).

```js
const r = e + await g.scriptExtension(e);            // e = "linux"; r = "linux.sh"
const n = path.join(__dirname, "../src/scripts", r); // correct full path
const i = n.replace(e, "run");                        // bug
```

`String.prototype.replace` changes only the first match. The full absolute path contains `linux` first inside the runner's own directory name (`linux-gh-runner`), before the trailing `linux.sh`. The replace corrupts the directory, not the filename. Running the same `node` command by hand with the runner's environment gave the same wrong path, so it was not specific to one job.

**Fix:** drop the action and install PHP with `apt`, as production does. Ubuntu 24.04 ships PHP 8.3. This also moves CI from PHP 8.2 to 8.3, which `composer.json` (`^8.2`) allows.

```yaml
- name: Install PHP 8.3 and required extensions
  run: |
    sudo apt-get update
    sudo apt-get install -y php8.3-cli php8.3-mbstring php8.3-bcmath php8.3-curl \
      php8.3-xml php8.3-zip php8.3-mysql php8.3-pgsql

- name: Install Composer
  run: |
    command -v composer >/dev/null 2>&1 && exit 0
    curl -sS https://getcomposer.org/installer | php
    sudo mv composer.phar /usr/local/bin/composer
    sudo chmod +x /usr/local/bin/composer
```

Renaming the runner would avoid this one collision, but it means re-registering with GitHub and changing DNS, and the same class of bug could return. Removing the dependency is more durable. Pinning another tag was rejected, because the bug is in a long-standing code path.

## 3. Incident 2: `migrate` fails with "could not find driver"

**Symptom:** the next run got further. `db:fresh-all` dropped tables on all five connections, then `migrate` failed.

```
could not find driver (Connection: sqlite, SQL: select exists (select 1 from "main".sqlite_master ...
```

**Cause:** every model pins one of the five real connections, so sqlite never holds data. But Laravel's migration repository, which records which migrations ran, always uses `config('database.default')` unless `migrate` gets `--database` (see `FreshAllDatabases.php`). `.env.testing.example` sets `DB_CONNECTION=sqlite` on purpose, so that bookkeeping never depends on the Tailscale databases being reachable. The runner was not set up for it.

**Fix:** two additions to `tests.yml`.

1. Add `php8.3-sqlite3` to the `apt-get install` step.
2. Create the file, because `database/testing.sqlite` is gitignored: `mkdir -p database && touch database/testing.sqlite`, next to `cp .env.testing.example .env.testing`.

## 4. Incident 3: GD extension is not installed

**Symptom:** 359 passed and 5 failed. Every failure was `LogicException: GD extension is not installed` from `FileFactory::image()`, used by the photo upload tests in `AnimalCrudTest` and `ReportSubmissionTest`.

**Cause:** the original `setup-php` step never listed `gd` either, so this was always going to fail once CI got far enough.

**Fix:** add `php8.3-gd` to the `apt-get install` step.

The first three incidents unblocked one another in order: the action, then the sqlite connection, then a missing extension. That was expected, because the workflow had never run to completion.

## 5. Incident 4: a real test bug

**Symptom:** the `backend` job passed, but the `browser` job's `ForcedPasswordChangeTest` failed all three tests.

```
RoleDoesNotExist: There is no role named 'adopter' for guard 'web'
```

**Cause:** the helpers in `tests/Concerns/SeedsMinimalDomain.php` call `seedRoles()` before assigning a role. `ForcedPasswordChangeTest::makeForcedResetUser()` builds a `User` by hand and calls `assignRole('adopter')`. It is a plain global function, so it never had access to `$this->seedRoles()`. The suite had never run cleanly in this environment, so the gap had not shown.

**Fix:** call `Role::firstOrCreate(['name' => 'adopter'])` before the assignment, as `seedRoles()` does for that role.
