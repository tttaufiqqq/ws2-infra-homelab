# CD

This article explains how a push to `main` deployed automatically to the fleet, how routing decided what to run, and the incidents found while building it.

> [!NOTE]
> **Archived.** This describes the deploy workflow that lived in the application repository. It was removed when the homelab was taken down. The current design is in [Architecture](architecture.md#4-delivery-pipeline).

## 1. Overview

`deploy.yml` fired on `workflow_run` once `tests.yml` ([CI](11-ci.md)) passed on `main`. A push to `main` was the only human action:

1. Green tests.
2. The fleet converges to that exact commit.
3. Smoke tests run.
4. If anything fails, the app server rolls back to the last known-good commit.

There was no approval gate and no manual `ansible-playbook` step. `workflow_dispatch` was an escape hatch only, for a forced re-run or a manual rollback to an older SHA.

It ran on `[self-hosted, linux, homelab, tailnet]` (`linux-gh-runner`, CT 111), because the databases and app server are reachable only inside the tailnet.

## 2. The `provision` and `deploy` tag split

`app-server.yml` does two different jobs, so every task carries a tag.

| Tag | Work |
|---|---|
| `provision` | Host setup: apt packages, UFW, certbot, Vault Agent, the scheduler's systemd unit |
| `deploy` | Per-push deploy: git pull, Composer, npm build, `.env` render, migrations, caches |

CD runs `--tags deploy`, unless the commit touched `infrastructure/ansible/`, when it runs the full playbook. It never runs `provision` alone and never seeds. The seed task and the `.provisioned` marker are tagged `provision`, so a deploy run cannot reach them even if the `provisioned_flag` check were wrong.

The five database playbooks are not split. They are small and already provision-shaped, so CD runs them in full, only when routing says so.

## 3. Path-based routing

The `plan` job diffs the commit against the SHA recorded as live on the app server (`storage/.last-good-deploy`, written only after smoke tests pass), not against the previous push. A batch of pushes or a retry after a failure therefore routes like a single clean push.

| Changed paths | `deploy-db` | `deploy-app` |
|---|---|---|
| App code only | No | `--tags deploy` |
| `app-server.yml`, `playbooks/tasks/**`, `templates/**`, `group_vars/**`, `inventory-ip.yml` | No | Full playbook |
| `playbooks/linux-*.yml` | Yes (`--limit databases`) | `--tags deploy` |
| `roles/**` | Yes | Full playbook |
| No `.last-good-deploy` marker | Yes | Full playbook |
| `workflow_dispatch` with `force_full: true` | Yes | Full playbook |

`deploy-app` always runs. If the diff against the recorded SHA fails (for example, the SHA is gone after a rebase), routing forces the full playbooks instead of guessing.

**`roles/**` widens both.** The roles refactor moved content into `roles/`, but the routing patterns were not updated. A roles-only change matched neither pattern and deployed as if nothing changed. A role's path does not say which target it affects, so any `roles/` change runs both in full.

## 4. Why `deploy-db` halts instead of rolling back

`deploy-app` can roll back by redeploying a previous SHA. `deploy-db` cannot, because an apt install or a UFW change has no well-defined undo. So it fails loudly and stops before `deploy-app` runs. Here, "fully automated" means "automatically halts".

Because there is no reversal, `deploy-db` first runs `php artisan db:backup` on the app server, through a one-shot Vault Agent config (`agent-backup.hcl`). That gives a fresh recovery point, not just last night's 02:00 run ([Backups](10-backups.md)). If the backup fails, provisioning never starts.

## 5. The `workflow_run` SHA gotcha

On a `workflow_run` trigger, `actions/checkout@v4` defaults to the default branch tip, not the commit that was tested. Every checkout pins `ref: ${{ github.event.workflow_run.head_sha || inputs.ref }}`. Without it, CD could deploy a `main` that differs from what CI certified.

## 6. Rollback and its migration caveat

On any `deploy-app` failure, the `rollback` job redeploys the SHA in `storage/.last-good-deploy` with `--tags deploy` and re-runs the smoke tests. If there is no last-good SHA, the `no-rollback-target` job fails loudly.

**Rollback restores code only.** Migrations are forward-only, and MySQL and MariaDB DDL is not transactional. If a deploy fails after `migrate`, the schema can be ahead of the rolled-back code. Automatic `migrate:rollback` is never attempted, because reversing a schema change on a database in an unknown state could destroy data. The job summary asks for a manual `php artisan migrate:status`.

## 7. Health check

The post-deploy check runs `vault agent -config=/etc/vault-agent/agent-verify.hcl`, which chains `migrate:status && db:refresh-status --fail-on-down && about --only=environment`.

Plain `db:refresh-status`, used by the scheduler, always exits 0, even with every connection down. It reports status and does not gate. That once hid a real incident: the scheduler ran with blank database passwords after a Vault Agent rollout and kept reporting `0/5 online` with exit code 0.

`agent-verify.hcl` uses `--fail-on-down`. If any connection is offline, it prints `DOWN: <connection> (<module>)` for each and exits non-zero, which stops the chain. Before, a partial outage such as only `postgres` down printed `4/5 online` and still passed. The workflow now checks the exit code first, and keeps the `5/5 online` substring as a second signal.

## 8. Secrets

CD credentials live in Vault at `secret/asw-cd`, not in GitHub Secrets:

- A CD-only SSH key (`ssh-keygen -t ed25519`) in `authorized_keys` on all six hosts, revocable separately from the admin key
- The shared become password
- The `asw-deploy` and `asw-app-server-agent` AppRole pairs that `group_vars/all.yml` needs

The `gh-runner` policy gained one read-only path, `secret/data/asw-cd`. Each step reads the key into `$RUNNER_TEMP`, masks values with `::add-mask::`, and shreds the key in an `if: always()` step.

## 9. Incidents

### 9.1 `login_unix_socket` broke on four hosts

**Symptom:** the first bootstrap run failed on all four MySQL and MariaDB hosts.

**Cause:** on 2026-07-20 the root passwords were unified. On MySQL and MariaDB, `ALTER USER ... IDENTIFIED BY` switches root from `unix_socket` to `mysql_native_password`. The playbooks connected with `login_unix_socket`, which stopped being valid, and nothing had re-run them since.

**Fix:** add a `mysql_root_password` group variable, sourced from Vault, and switch the `mysql_db` and `mysql_user` tasks to `login_user` and `login_password`.

### 9.2 `become_user: postgres` crashed with an ACL error

**Symptom:** `chmod: invalid mode: 'A+user:postgres:rx:allow'` in `linux-postgres.yml`.

**Cause:** privilege de-escalation needs `setfacl` to share temp files with an unprivileged user. Without the `acl` package, Ansible falls back to a non-Linux ACL dialect that fails on Ubuntu. `app-server.yml` already installed `acl`.

**Fix:** add the same `Install acl` task to `linux-postgres.yml`.

### 9.3 The frontend build never ran twice

**Symptom:** every frontend change since the first deploy shipped stale compiled assets.

**Cause:** `Build frontend assets` was guarded by `creates: public/build/manifest.json`. After the first deploy that file existed, so every later build was skipped. The task was also `command: npm ci && npm run build`. The `command` module never uses a shell, so `&&` was passed to `npm` as an argument. It only looked fine because the guard let it run once.

**Fix:** register the git task (`register: app_repo`), split the work into `Install npm dependencies` and `Build frontend assets`, and gate the build on `when: app_repo.changed`. Rollbacks and no-op redeploys now skip the slow `npm ci` on the single-core server.

## 10. Follow-up: fork pull request approval

The application repository is public, and the self-hosted runner holds Vault credentials that reach every database. GitHub advises that `pull_request` workflows on self-hosted runners are a risk, because anyone can open a PR. Whether **Require approval for first-time contributors** was enabled could not be checked from the build environment. Confirm it under **Settings**, **Actions**, **General**, **Fork pull request workflows**.
